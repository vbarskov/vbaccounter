# Изменения реестра

Используй инструменты MCP `vb_*`. Начни с `vb_status`, выбери компанию; при неоднозначности уточни её. Запрос пользователя на конкретное изменение разрешает внести это изменение. Не расширяй его до подачи отчёта, банковского платежа, изменения исходного приложения или создания расписания.

## Добавить обязательство

Вызови `vb_add_obligation`:

```json
{
  "accountId":"…",
  "title":"Название отчёта или платежа",
  "authority":"Получатель",
  "period":"Период",
  "due":"2027-01-15",
  "kind":"filing",
  "applicability":"unknown",
  "sourceUrl":"https://официальный-источник/…",
  "notes":"Основание и следующий шаг"
}
```

`kind`: `filing`, `payment` или `check`; `applicability`: `required`, `unknown`, `not-required`. Неизвестный срок можно не передавать. Не придумывай даты, адресата, режим налогообложения и применимость. Если устанавливаешь юридическую обязанность или официальный срок, сначала проверь актуальный первичный источник доступным веб-инструментом; иначе сохрани пользовательские сведения с соответствующей оговоркой или применимостью `unknown`.

## Уточнить применимость и срок

Для «проверил назначение: требуется/не требуется» сначала прочитай запись через `vb_get_obligation`, затем вызови `vb_set_applicability` с `accountId`, `id`, `applicability` (`required`, `unknown`, `not-required`). Необязательные поля: `due`, `sourceUrl`, `notes`, `evidencePath`. Для `required` и `not-required` обязательно передай основание хотя бы в одном из `notes`, `sourceUrl`, `evidencePath`.

Пример: пользователь уточнил, что отчёт требуется, и дал ссылку с крайним сроком. Проверь официальный источник, сохрани `applicability:required`, `due` в формате `YYYY-MM-DD`, `sourceUrl` и краткое объяснение в `notes`. Если пользователь подтвердил отсутствие обязанности, сохрани `not-required` с основанием. Если основания недостаточно — оставь/верни `unknown` и укажи следующий шаг. Пользовательское заключение можно зарегистрировать как его сведения, явно обозначив это в `notes`; это не проверка госорганом.

`vb_set_applicability` меняет локальный реестр, не отправляет запрос в госорган и не заменяет статус исполнения. Не ставь `accepted`/`paid` только из-за уточнения применимости.

## Изменить состояние

Сначала прочитай запись через `vb_get_obligation {"accountId":"…","id":"…"}`. Затем вызови `vb_update_obligation` с `accountId`, `id`, `status` и при необходимости `notes`, `evidencePath`.

- Отчёт: `needs-data` → `prepared` → `sent` → `accepted`; при отказе — `rejected`.
- Платёж: `pending` → `paid`.
- Проверка: `pending` → `done`.

Для `accepted` нужен доступный файл квитанции по `evidencePath`, для `paid` — файл подтверждения платежа. Уточни, какому обязательству соответствует документ, если это неясно. Не заменяй документ фразой «я сдал/оплатил». Существование файла само по себе не доказывает подлинность, содержимое или государственную проверку: сообщай, что статус сохранён на основании приложенного документа, и не заявляй о проверке в госоргане без отдельного подтверждения.

После изменения сообщи результат и следующее действие. Принятый отчёт и оплаченный платёж учитываются отдельно. Закрытие проверки не доказывает, что вся отчётность компании выполнена. Исходный `vb-accounting.json` остаётся доступным только для чтения, статусы плагина хранятся отдельно.

## Уведомления

Для «покажи уведомления» вызови `vb_list_notifications {"accountId":"…","unreadOnly":true,"includeDemo":false}`: он читает сохранённый список без генерации событий и отметки прочтения. `vb_check_notifications {"accountId":"…","includeDemo":false}` выполняет новую проверку, создаёт события и сохраняет историю повторов. По просьбе пользователя используй `vb_ack_notification {"id":"…","snoozeUntil":"2026-11-10"}`: без `snoozeUntil` — отметка прочтения; с датой `YYYY-MM-DD` — отсрочка. Ни одно действие не закрывает обязательство и не сдвигает срок. `vb_notification_settings` читает настройки, параметры `enabled` и `leadDays` меняют их по запросу.

Проверка не запускается сама. Если пользователь отдельно просит расписание, используй доступные инструменты автоматизаций хоста, реальный общий постоянный каталог состояния из `vb_status` вне кэша плагина и тихий режим при отсутствии новых значимых действий. Укажи зависимость локального задания от работающего компьютера и хоста. Ошибка чтения источника и неизвестная применимость требуют внимания, а не сообщения «всё выполнено». Без инструментов автоматизаций расписание не создавай и не обещай.
